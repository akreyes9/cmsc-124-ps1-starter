## Question 1

**Pick 3 of the 10 categories. For each, pick a language that gives it to you for free and say what that language pays for it in memory or speed compared to what we built, and where you would notice.**

I chose strings, associative arrays, and lists in Python because they are related to the way I work with RAG pipelines. I use list comprehensions where each element is a dictionary containing retrieval output. Python's higher level of abstraction makes this simpler to read and write. However, the convenience still has costs, and those costs depend on the type and operation.

**Strings.** Python provides `str`, which represents Unicode text and is immutable. Our `dt_str` stores bytes, length, and capacity, and allows appending to the same string. Python string concatenation can require a new object and copying the existing text. Repeated concatenation can therefore become quadratic; using `join()` avoids that pattern. Our append grows the buffer geometrically, so it can reuse spare capacity and avoid copying the entire string on every append. The C version also pays for unused capacity, and its byte storage does not provide Python's Unicode text handling. In a RAG pipeline, this difference could matter when combining many retrieved passages into a prompt. I have not benchmarked a C version of my pipeline, so this is a possible cost rather than something I have measured. [Python string documentation](https://docs.python.org/3/library/stdtypes.html#text-sequence-type-str), [sequence concatenation notes](https://docs.python.org/3/library/stdtypes.html#common-sequence-operations).

**Associative arrays.** Python's `dict` handles hashing, table resizing, and insertion order. In CPython, keys and values are Python objects with bookkeeping such as type information and reference counts. These objects and the table consume memory beyond the actual retrieval data. Our `dt_map` is more restricted: it copies string keys and stores tagged `dt_value` values in bucket chains, with a separate array for insertion order. An integer value fits directly in `dt_value` rather than requiring a separate Python integer object. However, our map also pays for copied keys, node allocations, and ordering storage. Its fixed 64 buckets can develop long chains as it grows, while Python resizes its table. I would not claim our map is always faster or smaller without measurement. For my list of retrieval-result dictionaries, the object overhead could become noticeable when keeping many results in memory. [CPython dictionary implementation](https://docs.python.org/3/faq/design.html#how-are-dictionaries-implemented-in-cpython), [Python object structures](https://docs.python.org/3/c-api/structures.html#base-object-types).

**Lists.** CPython's `list` is a dynamic array of object references, unlike our linked `dt_list`. It reserves extra space for growth and stores references to the dictionaries, rather than copying their contents into each list position. Inserting at the front shifts existing references, whereas our `cons` allocates one cell and shares the tail. On the other hand, Python supports constant-time indexing and stores the length; our list must follow cells to reach a later item or calculate its length. Our separate cells also cost memory and allocations. For the retrieval outputs I build with comprehensions, Python's list is convenient for collecting and accessing results. The tradeoff would matter more if I repeatedly inserted results at the front of a large list. [CPython list implementation](https://docs.python.org/3/faq/design.html#how-are-lists-implemented-in-cpython).

For my RAG work, I would still choose Python because it is simpler to read and write. It lets me focus on making the system work instead of getting stuck on lower-level storage and allocation details. I would reconsider the representation if measurements showed that storing or processing retrieval results was using too much memory or time.

## Question 2

**You wrote the tag check in `dt_value_as_int` by hand. Some languages don't let you. They make the tagged union a language construct, so the compiler writes the check for you, refuses to compile a read that skips it, and refuses to compile a set of cases that misses one. Rust's `enum` and `match` work this way, and so do ML's datatypes and Swift's enumerations with associated values. What does the C version let you do that a compiler enforcing the check wouldn't, and is any of it worth wanting?**

C lets you do several things that a compiler-enforced tagged union would reject. You can read the data inside a union without checking the tag, so a float's bits can be treated as an int. You can build a value whose tag claims one type while the data holds another, or leave the tag unset entirely. You can also skip cases when handling a tag, and you can add a new type later without touching existing code, because the tag is just a number and nothing forces old handlers to account for the new one. A compiler that enforces the check forbids the first three outright and, for the last, makes you update every place that handles the cases.

Most of this isn't worth wanting. Reading the wrong type, mismatching tag and data, and missing a case are all plain mistakes, and in C they surface only as garbage values or bugs at runtime. The one real freedom is skipping a check you have already performed, since testing the same tag twice is redundant and costs a little time in hot code. But that freedom isn't lost in Rust, which allows unchecked access when you explicitly mark the code as `unsafe`. Adding a type without revisiting old handlers can matter in some designs, but it is a minor convenience next to the safety it costs, because the forced update is exactly how the compiler guarantees no case goes unhandled. In the end, C's extra freedom is mostly the freedom to make mistakes, and the compiler-enforced version removes those mistakes while keeping the useful capabilities available on request.

## Question 4

**Compare access after release with an allocation that remains unreleased at the driver's final check. What damage can each cause in a long-running server? How does that answer change for a command-line tool that exits in a second?**

Using memory after it has been freed is the more dangerous mistake, because the program touches memory it no longer owns. By then that spot may already belong to something else, so reading it gives wrong values, and writing to it silently corrupts other data. The damage happens at the moment of the bad access, and it can cause crashes, wrong results, or even security holes if someone can control what ends up in that spot. An allocation that is never released is a different kind of mistake. Nothing breaks at the moment it happens, because the memory is simply reserved and never used or given back. It is wasted space but not wrong behavior.

In a long-running server, both are serious for different reasons. A use after free can crash or corrupt the server on any request that hits it, and since the server handles requests constantly, it will eventually hit it. A leak is a slow problem: each request may waste a small amount, but because the server never stops, the waste keeps adding up until memory runs out and the server slows down, crashes, or gets killed.

For a command-line tool that exits in a second, the answer changes for the leak but not for the use after free. When a program exits, the operating system takes back all of its memory, including anything that was never released, so a leak has no time to build up into a problem. The use after free is just as harmful as before, because it only takes one bad access to corrupt data or crash the program, no matter how short its run is. So running time decides how much a leak matters, but it makes no difference to how dangerous a use after free is.
